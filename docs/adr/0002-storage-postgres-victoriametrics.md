# 0002. 业务数据用 PostgreSQL，时序指标用 VictoriaMetrics

- 状态：已接受
- 日期：2026-09-23

## 背景

系统需要存储两类特征完全不同的数据：

| | 业务数据 | 时序指标 |
|---|---|---|
| 例子 | 节点、GPU、以后的预约与任务 | 每 10 秒一次的利用率、显存、温度 |
| 写入量 | 少 | 持续写入，规模假设下约为每秒数百个样本 |
| 查询方式 | 按主键查、关联查、事务 | 按时间范围查、降采样、聚合 |
| 修改 | 频繁更新 | 只追加，不修改 |

此外，断网恢复后 Agent 会补发带历史时间戳的数据（见 0001），存储必须接受这类"迟到"的样本。

## 备选方案

### A. 全部存入 PostgreSQL

- 优点：只有一个存储组件。
- 缺点：用普通表存时序数据，数据量和查询性能都会随时间变差，降采样和过期清理都要自己实现。

### B. PostgreSQL + TimescaleDB 扩展

- 优点：一个数据库、一套 SQL，就能同时处理两类数据。
- 缺点：需要安装扩展，对 PostgreSQL 的版本和镜像有要求；查询语言不是 PromQL，无法直接复用 Grafana 等生态中的面板。

### C. PostgreSQL + Prometheus

- 优点：生态最成熟。
- 缺点：Prometheus 以拉取为主，作为推送目标需要开启 remote write receiver；默认不接受乱序和过旧的样本，断网补发需要额外配置时间窗口。

### D. PostgreSQL + VictoriaMetrics（选定）

- 优点：单二进制部署，资源占用低；兼容 PromQL（MetricsQL）；支持通过导入接口写入带历史时间戳的数据，适合断网补发；可以直接对接 Grafana。
- 缺点：多一个存储组件。

## 决策

采用方案 D：

- PostgreSQL 存业务数据，表结构以 `migrations/` 为准。
- VictoriaMetrics 存时序指标，指标命名遵循 `conventions.md` 第 5 节。
- 高基数、短生命周期的数据（如 GPU 进程列表）两边都不存，只保存在 Controller 内存中作为当前快照。

## 后果

好处：

- 两类数据各自使用最合适的存储，查询写法都很自然。
- 断网补发可以直接写入。
- 需要时可以直接用 Grafana 调试或临时查看数据。

代价：

- 需要运维两个存储组件，包括备份和升级。
- 两个存储之间不能做关联查询，需要在 Controller 中按 `node_id` 组装数据。
- 需要约束标签基数，禁止把 PID、命令行等作为标签。

重新评估的条件：如果维护两个组件的成本明显过高，可以评估迁移到方案 B。
