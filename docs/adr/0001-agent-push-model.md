# 0001. Agent 主动连接 Controller，使用 gRPC 双向流

- 状态：已接受
- 日期：2026-09-23

## 背景

每台 GPU 服务器需要把指标上报到中心。后续里程碑中，中心还要向服务器下发指令：M3 的迁移任务、M4 的启停任务。

约束如下：

- 服务器位于校园网内，网络会整体中断，也可能只有部分机器不可达。
- 服务器是多人共用的，应尽量少占端口、少改防火墙。
- 中心需要准确判断每台机器是否在线。
- 维护者只有一人，组件越少越好。

## 备选方案

### A. 中心拉取（Prometheus 模式）

Controller 定时访问每台服务器上 Agent 暴露的 HTTP 端口。

- 优点：成熟，可以直接使用 node_exporter 等现成工具。
- 缺点：每台服务器都要开放监听端口，Controller 必须能反向访问所有机器；断网期间的数据取决于 Agent 是否缓存，而拉取模型本身没有补数据的机制；下发指令还需要另建一条通道。

### B. Agent 推送，使用普通 HTTP 请求

Agent 定时 POST 指标。

- 优点：实现最简单。
- 缺点：没有下行通道，中心下发指令只能靠 Agent 轮询，延迟与请求量二者不可兼得；在线状态只能从"多久没收到请求"推断。

### C. 引入消息中间件（MQTT / NATS）

- 优点：天然支持双向通信和断线重连。
- 缺点：多一个需要部署和维护的组件；消息格式和可靠性语义需要额外设计。

### D. Agent 主动建立 gRPC 双向流（选定）

Agent 启动后连接 Controller，保持一条长连接，上行发送注册、心跳和指标，下行接收确认和指令。

## 决策

采用方案 D。Agent 作为客户端主动连接 Controller，每个 Agent 维持一条 gRPC 双向流：

- 上行：`Hello`（注册与静态信息）、`Heartbeat`、`MetricsBatch`（带单调递增序号）。
- 下行：`Ack`（确认已收到的序号）、`Command`（M1 暂不使用）。

## 后果

好处：

- 只有 Controller 需要开放一个端口，服务器无需开放任何入站端口。
- 流的建立和断开本身就是在线信号，配合心跳超时即可判断节点状态。
- 上下行共用一条连接，M3、M4 下发指令时无需再修改架构。
- 接口由 proto 定义，并由 `buf breaking` 保证兼容性。

代价：

- 需要自己实现重连退避、keepalive、本地缓冲与按序号补发（见 M1 范围文档 3.5 节）。
- 流是有状态的，每个 Agent 固定连到某一个 Controller，横向扩展多个 Controller 较难。当前阶段可以接受，见 0003。
- 无法直接复用 Prometheus 生态中的 exporter，采集器需要自己编写。

重新评估的条件：需要把第三方 exporter 纳入监控时，可考虑让 Agent 同时抓取本地 exporter，再通过流转发。
