# 0003. 一期使用单 Controller，不引入 K8s、Redis、etcd

- 状态：已接受
- 日期：2026-09-23

## 背景

- 规模小：预计不超过 20 台服务器，每台不超过 8 张 GPU。
- 只有一人开发和维护。
- 最常见的故障是**校园网中断**，而不是 Controller 所在机器损坏。
- 必须兼容不通过平台启动的程序，不能要求所有人改变现有的使用方式。

## 备选方案

### A. 使用 Kubernetes（加 GPU Operator）管理 GPU 服务器

- 优点：调度、容器化、高可用都有现成方案。
- 缺点：需要把所有服务器纳入集群，并要求大家通过容器提交任务，与"兼容不通过平台启动的程序"的约束冲突；集群本身的运维成本远超项目规模。

### B. 多个 Controller 加 etcd/Raft 选主

- 优点：Controller 没有单点。
- 缺点：一致性、选主、Agent 路由都要处理，复杂度成倍增加；而且解决的并不是最常见的故障。校园网断开时，多个 Controller 同样不可达。

### C. 引入 Redis 保存在线状态和缓存

- 优点：Controller 重启后状态不丢。
- 缺点：在线状态本来就可以由 Agent 重连重建，持久信息已存入 PostgreSQL，多一个组件的收益很小。

### D. 单 Controller，可靠性由 Agent 端保证（选定）

## 决策

采用方案 D。一期只部署一个 Controller，不引入 K8s、Redis、etcd。应对故障的方式如下：

- Agent 断线后按指数退避加随机抖动的方式重连。
- 断线期间 Agent 在本地缓冲数据，恢复后按序号补发，Controller 对补发做幂等去重。
- Controller 重启后，节点状态由 PostgreSQL 中的持久信息加上 Agent 重连信息恢复（恢复对账）。
- Controller 由 systemd 或 compose 自动拉起，PostgreSQL 定期备份。

## 后果

好处：

- 部署只需一条 compose 命令加各服务器上的一个 Agent 二进制。
- 代码路径简单，故障容易排查。
- 服务器上的现有使用方式不需要任何改变。

代价：

- Controller 所在机器停机期间，页面不可用。数据由 Agent 缓冲，缓冲容量内不会丢失。
- 以后需要高可用时要做改造，主要改动点在 Agent 连接的路由上。

重新评估的条件（满足任一即重新讨论）：

- M4 调度上线后，Controller 停机会直接导致任务无法提交，且停机频率超出可接受范围。
- 节点数超过 100，或单 Controller 出现性能瓶颈。
- 需要跨校区、跨网络部署。
